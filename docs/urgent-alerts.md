# 긴급 뉴스 알림

`긴급 뉴스 알림` Actions가 24시간 매시 7·22·37·52분에 실행됩니다. GitHub 예약 지연이나 뉴스 검색 반영 지연이 있어 즉시 알림을 보장하지 않습니다. AI API는 호출하지 않습니다.

`config/alerts.yml`에서 검색어·제목 판정 기준·알림 한도를 조정합니다. 기관 중대 이슈, 석유/가스 시설 사고, 공급 차질, 긴급 정책, 대규모 불법 유통을 선별합니다. 훈련·예방·전망 기사는 제외합니다. 키워드 판정이므로 누락이나 오탐이 있을 수 있습니다. 메시지에 제목·매체·시각·판정 이유·원문 링크를 제공하며, 보고 전 사실관계 확인이 필요합니다.

추가 관심 주제는 `topics`에서 관리합니다. 에너지시장감시단(에너지·석유시장감시단 등 표기 포함)의 새 조사·발표와 석유공사·가스공사 통합(에너지자원공사 포함)을 별도 검색 두 번으로 확인합니다. 이들 주제의 공식 부인·철회·검토·이해관계자 반응은 긴급성 제외 필터로 버리지 않고 `📰 관심 주제 업데이트`로 표시합니다. 칼럼·주가 기사와 단순 통합 전산·안전 시스템 소식은 제외합니다. 사용자 제외 키워드, 휴식 시간, 발송 상한, 중복 제거와 7일/500건 이력 제한은 계속 적용합니다. 제목만으로 판정하므로 본문에만 등장한 관련 사항은 놓칠 수 있습니다.

같은 검색어를 `config/news.yml`의 아침 스크랩에도 넣었습니다. 통합 소식은 공공기관, 감시단 소식은 에너지 분야에 분류하며 기존 분야별 발송 한도를 적용합니다. Gemini Spark의 매시간 예약에도 두 주제를 추가했고, 사고 수준의 긴급성이 없어도 새로운 사실·발표를 보고하도록 설정했습니다. Gemini 전송에는 [별도의 승인 제약](gemini-spark.md)이 있습니다.

## 저장과 중복

Supabase에 `migrations/202609190002_alerts.sql`을 적용합니다. 기존 GitHub Secrets(두 Supabase 값과 두 Telegram 값)를 그대로 씁니다. 새로운 비밀키나 AI 키는 필요 없습니다.

`news_alert_state` 단일 행에 발송 기록만 저장합니다. 기사 본문·수집 결과·원문 URL은 저장하지 않습니다. 기록 필드는 기사 ID, 최대 500자 제목, 판정 분류, 수신방, 중복 판정용 주제, 발송 시각입니다. **7일 또는 최근 500건** 중 먼저 도달하는 범위만 유지합니다. 최악의 경우에도 JSON 데이터는 대략 1 MB 미만이며 실제 대부분은 더 작습니다. 검색 결과 전체는 실행 종료 시 폐기합니다. 기존 초안/제외 테이블의 저장 방식은 바꾸지 않습니다.

최초 실행은 최근 15분 기사부터 시작하며, 이후 최근 6시간 기사를 재확인합니다. 날짜 불명·미래 기사는 제외합니다. URL이 같거나 같은 분류에서 제목이 매우 비슷하면 재발송하지 않습니다. 숫자가 달라진 별도 URL의 후속 보도는 새 후보가 될 수 있습니다. 방마다 한 번에 최대 3건을 보내고 나머지는 다음 실행에서 다시 확인합니다. 기본값은 기존 범위를 유지하는 `standard`, 일일 상한 없음입니다.

## Telegram 명령과 단톡방

`migrations/202609190003_bot_settings.sql` 적용 → Vercel 배포 완료 → Actions의 `봇 명령 연결`을 수동 실행합니다. GitHub의 기존 `TELEGRAM_CHAT_ID`는 소유자 개인 대화 ID여야 합니다. Vercel에 Telegram 토큰을 추가할 필요는 없습니다. 기존 Supabase 키에서 파생한 서명으로 webhook을 검증하며 명령 응답은 Telegram webhook 응답 방식을 사용합니다.

소유자만 설정을 변경할 수 있습니다. 그룹에서는 봇을 초대한 다음 소유자가 `/subscribe@news_joongyubot`을 보내야 뉴스가 시작됩니다. 그룹의 다른 사용자는 설정을 바꿀 수 없습니다. 개인방을 포함해 최대 5개 방이며 각각 독립된 설정을 갖습니다. 아침/주간 동향도 구독방에 발송합니다. 담당자 검토 링크는 소유자 개인방에만 발송합니다. 이메일 수신 설정은 이 명령으로 변경되지 않습니다.

| 명령 | 기능 |
| --- | --- |
| `/help`, `/status` | 사용법, 현재 방 설정 |
| `/usage` 또는 `usage` | 소유자 개인 대화에서 GitHub 사용량·API 잔여 한도 |
| `/logs` 또는 `logs` | 최신 초안·긴급 점검 건수와 수집/발송/긴급 실행 결과 |
| `/logs collect`, `/logs alerts`, `/logs dispatch` | 분야별 최근 3회 실행 시각/상태/상세 로그 링크 (`수집`, `긴급`, `발송`도 가능) |
| `/subscribe`, `/unsubscribe` | 현재 방 구독/해제 |
| `/urgent on`, `/urgent off` | 긴급 알림 켜기/끄기 |
| `/daily on`, `/daily off` | 아침/주간 동향 켜기/끄기 |
| `/mode standard`, `/mode strict` | 기존 기준/주제 중복 억제와 추가 제외 기준 |
| `/limit 0` 또는 `/limit 5` | 하루 상한 없음 또는 지정 건수(1~20) |
| `/quiet 22-07`, `/quiet off` | 긴급 알림 휴식 시간(KST), 해제 |
| `/watch add 키워드`, `/watch remove 키워드`, `/watch list` | 관심 키워드 관리 |
| `/exclude add 키워드`, `/exclude remove 키워드`, `/exclude list` | 제외 키워드 관리 |

키워드는 정규식이 아닌 제목의 문자 포함 여부로 판정하며 각 종류 최대 10개, 단어당 30자입니다. 관심 키워드를 추가하면 일반 소식도 알릴 수 있습니다. 모든 방의 관심 검색어는 추가 검색 한 번으로 묶습니다. `strict`는 같은 지역·시설·사건 주제를 24시간 억제하고 수상·분석·검토 등의 제목을 더 제외하므로 중요한 후속 보도를 놓칠 수 있습니다.

명령은 webhook으로 즉시 처리하며 이를 위해 Actions를 추가 실행하지 않습니다. 설정은 `news_bot_settings` 1행, 최대 64KB입니다. 일반 채팅은 저장하지 않으며 최근 변경 명령 30개의 처리 ID와 응답만 중복 처리 방지를 위해 보관합니다. DB 갱신은 revision을 비교하여 충돌을 방지합니다. 뉴스 검색/발송은 기존 15분 예약에 따릅니다. 봇을 그룹에서 내보내기 전에 `/unsubscribe`를 보내면 불필요한 발송 실패를 막을 수 있습니다.

워크플로를 직렬 실행하고 성공한 메시지마다 DB에 기록합니다. DB 읽기/첫 저장 실패 시 발송하지 않습니다. Telegram이 수신한 직후 프로세스가 중단되거나 DB 기록이 실패하면 재시도 시 중복 가능성이 있습니다(외부 발송과 DB 저장은 하나의 트랜잭션이 아님).

## 운영과 비용

`/usage`는 기존 뉴스 점검 실행이 저장한 최신 수치를 즉시 보여줍니다. 공개 여부와 체크인된 모든 작업의 표준 Ubuntu runner 여부, 해당 저장소 `GITHUB_TOKEN`의 REST API 남은 호출 횟수/초기화 시각, 현재 캐시 용량을 조회합니다. 공개 저장소·표준 runner 실행분은 월 무료 실행분에서 차감하지 않습니다. API 호출 횟수는 AI 토큰이나 유료 크레딧이 아니며, 계정 전체 청구액·유료 잔액은 권한이 없어 조회하지 않습니다. 캐시는 현재 용량/무료 기준 10 GiB를 표시하며 청구 기간 중 누적·최대 사용량이나 계정 전체 아티팩트 저장량을 뜻하지 않습니다. [API 한도](https://docs.github.com/en/rest/rate-limit/rate-limit), [비용 기준](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

추가 예약/작업을 만들지 않고 기존 15분 실행에서 GitHub 읽기 요청 6회와 DB 스냅샷 교체만 수행합니다. `dry_run`에서는 저장하지 않습니다. DB에는 기존 설정 행의 `github_usage` 한 항목만 덮어쓰며 토큰은 저장하지 않습니다. 실행 기록은 수집·발송·긴급 각각 최근 3개(총 9개)의 ID·상태·시각만 유지하며 현재 스냅샷을 만드는 실행은 제외합니다. 원문 로그·오류 내용은 저장하지 않고 GitHub 링크로 제공합니다. 봇 명령 자체는 Actions/GitHub API를 호출하거나 DB에 기록하지 않습니다. 갱신 실패는 뉴스 발송을 막지 않고 이전 스냅샷을 유지합니다. 45분 이상 지난 값과 이미 초기화 시간이 지난 호출 잔여량은 경고를 표시합니다. 그룹에는 수치를 노출하지 않으며 소유자 개인 대화에서만 조회합니다.

`/logs`는 명령 시점에 DB의 최신 아침 초안과 긴급 점검 요약을 읽습니다. 초안에 저장된 대표/중복 기사 수, 분야별 건수, 생성 시각과 긴급 검색의 수집/발송 건수를 표시합니다. 새 초안에는 수집/신선도/분류 통과 단계별 건수 5개만 추가하고 원시 기사 전문은 저장하지 않습니다. 긴급 기록에는 마지막 점검의 종료 시각·후보/실패 건수를 추가합니다. GitHub 워크플로 성공은 시험 실행도 포함할 수 있고 부분적인 이메일 실패가 있어도 성공할 수 있으므로 실제 발송은 상세 로그에서 확인하도록 안내합니다.

- 알림이 없으면 Telegram은 조용히 유지합니다.
- 수동 `Run workflow`에서 `dry_run`은 발송/저장 없이 후보만 확인합니다.
- `send_test`는 정상 점검 후 가동 확인 메시지를 1회 보냅니다. 예약 실행에는 보내지 않습니다.
- 일시 중지는 GitHub Actions에서 워크플로를 Disable 하거나 설정의 `enabled: false`를 커밋합니다.
- 하루 96회, 30일 약 2,880회 실행. 표준 Ubuntu runner, 최대 실행 4분, 4개 병렬 검색으로 제한합니다. 아티팩트 업로드·기사 커밋·Vercel 재배포를 하지 않습니다.
- 현재 공개 저장소의 표준 runner 실행은 무료입니다. 비공개로 전환하면 포함된 실행 시간/과금 기준을 다시 확인해야 합니다. [GitHub 기준](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
- 오류는 Actions 실행 실패로 표시되므로 GitHub 알림 설정에서 실패 알림을 받을 수 있습니다. 마지막 정상 실행은 DB의 `last_checked_at`으로 확인합니다.
