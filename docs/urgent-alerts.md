# 긴급 뉴스 알림

`긴급 뉴스 알림` Actions가 24시간 매시 7·22·37·52분에 실행됩니다. GitHub 예약 지연이나 뉴스 검색 반영 지연이 있어 즉시 알림을 보장하지 않습니다. AI API는 호출하지 않습니다.

`config/alerts.yml`에서 검색어·제목 판정 기준·알림 한도를 조정합니다. 기관 중대 이슈, 석유/가스 시설 사고, 공급 차질, 긴급 정책, 대규모 불법 유통을 선별합니다. 훈련·예방·전망 기사는 제외합니다. 키워드 판정이므로 누락이나 오탐이 있을 수 있습니다. 메시지에 제목·매체·시각·판정 이유·원문 링크를 제공하며, 보고 전 사실관계 확인이 필요합니다.

## 저장과 중복

Supabase에 `migrations/202609190002_alerts.sql`을 적용합니다. 기존 GitHub Secrets(두 Supabase 값과 두 Telegram 값)를 그대로 씁니다. 새로운 비밀키나 AI 키는 필요 없습니다.

`news_alert_state` 단일 행에 발송 기록만 저장합니다. 기사 본문·수집 결과·원문 URL은 저장하지 않습니다. 기록 필드는 기사 ID, 최대 500자 제목, 판정 분류, 발송 시각입니다. **7일 또는 최근 500건** 중 먼저 도달하는 범위만 유지합니다. 최악의 경우에도 JSON 데이터는 대략 1 MB 미만이며 실제 대부분은 더 작습니다. 검색 결과 전체는 실행 종료 시 폐기합니다. 기존 초안/제외 테이블의 저장 방식은 바꾸지 않습니다.

최초 실행은 최근 15분 기사부터 시작하며, 이후 최근 6시간 기사를 재확인합니다. 날짜 불명·미래 기사는 제외합니다. URL이 같거나 같은 분류에서 제목이 매우 비슷하면 재발송하지 않습니다. 숫자가 달라진 별도 URL의 후속 보도는 새 후보가 될 수 있습니다. 한 번에 최대 3건을 보내고 나머지는 다음 실행에서 다시 확인합니다.

워크플로를 직렬 실행하고 성공한 메시지마다 DB에 기록합니다. DB 읽기/첫 저장 실패 시 발송하지 않습니다. Telegram이 수신한 직후 프로세스가 중단되거나 DB 기록이 실패하면 재시도 시 중복 가능성이 있습니다(외부 발송과 DB 저장은 하나의 트랜잭션이 아님).

## 운영과 비용

- 알림이 없으면 Telegram은 조용히 유지합니다.
- 수동 `Run workflow`에서 `dry_run`은 발송/저장 없이 후보만 확인합니다.
- `send_test`는 정상 점검 후 가동 확인 메시지를 1회 보냅니다. 예약 실행에는 보내지 않습니다.
- 일시 중지는 GitHub Actions에서 워크플로를 Disable 하거나 설정의 `enabled: false`를 커밋합니다.
- 하루 96회, 30일 약 2,880회 실행. 표준 Ubuntu runner, 최대 실행 4분, 4개 병렬 검색으로 제한합니다. 아티팩트 업로드·기사 커밋·Vercel 재배포를 하지 않습니다.
- 현재 공개 저장소의 표준 runner 실행은 무료입니다. 비공개로 전환하면 포함된 실행 시간/과금 기준을 다시 확인해야 합니다. [GitHub 기준](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
- 오류는 Actions 실행 실패로 표시되므로 GitHub 알림 설정에서 실패 알림을 받을 수 있습니다. 마지막 정상 실행은 DB의 `last_checked_at`으로 확인합니다.
